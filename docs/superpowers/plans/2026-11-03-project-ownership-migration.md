# Infinite Canvas 项目自有化迁移

**状态：** 阶段 A 已提交并推送到 PR [#20](https://github.com/Smithhss/infinite-canvas/pull/20)，Quality CI 已通过；尚未合并、发布或部署生产。

**目标：** 在保留 MIT 原始版权和必要兼容边界的前提下，让用户入口、发布链路、扩展生态、视觉语言和文档逐步归属当前项目，不再依赖上游品牌与公共发布地址。

## 原则

1. 先完成可验证兼容，再替换名称；不因品牌迁移破坏已有安装、插件更新或用户数据。
2. 不复制 LibTV 或其他产品的源码、字体、图标、图片和受版权保护的素材，只借鉴信息层级、密度和交互原则。
3. 所有迁移按阶段验收，每个阶段都能单独回滚。
4. 浏览器本地数据迁移必须先备份、版本化、校验和原子写入；未知版本或损坏数据拒绝覆盖。
5. 未经明确授权，不提交、不推送、不发布镜像、不上架 npm 包、不部署生产。

## 阶段 C：浏览器存储命名空间

**状态：** 只读扫描与临时库演练已完成，正式迁移未开始。

当前使用 `infinite-canvas` IndexedDB、`infinite-canvas:*` localForage key 和故事板折叠偏好。直接改名会丢失画布、资产、生成历史或设置。

2026-11-03 已通过 8 个对象仓、81 个图片文件、6 个本地偏好键及其他记录的独立临时库复制与逐仓校验；演练结束后只删除临时库，正式库、正式读取入口和正式写入入口均未改动。记录见 `docs/superpowers/audits/2026-11-03-browser-storage-migration-rehearsal.md`。

迁移顺序：

1. 只读扫描旧库，生成项目数、节点数、连接数、资产数、生成记录数和占用体积摘要。
2. 在临时新库写入完整副本，不删除旧库。
3. 逐项校验 schema、版本、关键 ID、二进制大小和可读取性。
4. 写入迁移标记；应用首次启动时优先读取新库。
5. 至少保留一个版本的双读或恢复入口。
6. 用户确认后才提供清理旧库操作。

**停止线：** 任一未知版本、损坏记录、空间不足或校验失败都必须停止迁移并保留旧库。

## 阶段 E：自有文档域名

**状态：** 等待域名、DNS 控制权和托管目标确认，未修改生产配置。

当前文档是独立的 Next.js 应用，可走 GitHub Pages、文档容器或任意支持 HTTPS 的静态/容器托管；应用侧通过构建变量 `VITE_DOC_URL` 打开文档入口。

切换前必须确认：

1. 最终域名及是否需要保留旧地址重定向。
2. DNS 托管方与修改权限，避免只拿到域名但无法切换记录。
3. 目标托管方式：GitHub Pages、`infinite-canvas-docs` 容器或用户现有反向代理。
4. TLS 证书、缓存、语言路由和 `/docs` 重写是否保持不变。
5. 回滚时恢复的 DNS 记录和旧站点地址。

代码侧入口：

- `web/src/constant/env.ts` 的 `DOCS_URL` 与构建环境变量 `VITE_DOC_URL`。
- `docs/next.config.mjs` 的根路径和 `/docs/:path*` 重写。
- `.github/workflows/github-pages.yml` 与 `.github/workflows/docs-docker-image.yml` 的发布目标。
- 外部 DNS、TLS 和反向代理配置；这些不属于仓库提交。
